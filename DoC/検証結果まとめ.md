## 0. 三行まとめ

1. **decode時間は「GPUに載せた層数」に対して直線的に減る**（R²=0.995）。加算モデルがそのまま成立する。
2. その逆数である速度は双曲線になるため、**部分オフロードは終端でしか効かない**。50%載せても全体の伸びの14%しか得られず、半分の効果を得るには89%の層が必要。
3. **同じ層数でも配置が断片的だと遅くなる**。1層おきの交互配置は連続配置より4.23%遅く、境界1回あたり365 µs（95%CI: 181〜550 µs）のコストが乗る。

---

## 1. 何を検証したか

エッジ端末向けSLM推論において、**モデルの一部の層だけをアクセラレータに載せる実行形態（部分オフロード）**の挙動を、PC環境（RTX 5070 Ti + Core i7-10700F）で定量把握した。

対象は Qwen2.5-3B-Instruct（36層）。層ごとにCPU/GPUを任意に指定できるハーネスを PyTorch + accelerate で自作し、以下2点を測った。

| # | 問い | 手段 |
|---|---|---|
| ① | オフロード率と速度の関係はどんな形か | GPU層数を 0〜36 の10点でスイープ |
| ② | 同じオフロード率でも「分断のしかた」で差が出るか | オフロード率50%固定のまま境界数を 2/6/18/36 に振る |

②が本検証の中核である。4条件は計算量が完全に同一（GPU 18層・CPU 18層）なので、差はデバイス境界を跨ぐコストのみに由来する。

---

## 2. 結論

### 2.1 decode時間は層数に線形（仮説①→支持）

```
decode_ms = 485.21 − 11.459 × (GPUに載せた層数)      R² = 0.99542
```

| | 1層GPUに移すごとの短縮 |
|---|---|
| 事前予測（帯域比から算出） | 11.3 ms/層 |
| 実測 | **11.46 ms/層（乖離1.4%）** |

加算モデル `t(n) = (N−n)·t_cpu + n·t_gpu` が係数レベルで成立した。

### 2.2 部分オフロードは終端でしか効かない（仮説②→支持）

| GPU層数 | オフロード率 | tokens/sec | 全CPU比 |
|---|---|---|---|
| 0 | 0% | 2.00 | 1.00倍 |
| 18 | 50% | 約3.7 | 約1.83倍 |
| 32 | 89% | 7.86 | 3.93倍 |
| 36 | 100% | 13.95 | **6.98倍** |

> **全体の高速化の半分を得るには、36層のうち32層（89%）をGPUに載せる必要がある。**

処理時間が加算である以上、遅い側が残っている限り総時間は下がらない。

**一般則（Step 4で導出・検証）**: 全体の高速化を R とすると、50%オフロードで得られるのは全体の伸びの **1/(R+1)** である。

| 加速器の速さ（R） | 50%オフロードで得られる割合 |
|---|---|
| 7倍 | 12.6%（実測14.0%） |
| 14倍 | 6.5%（実測8.2%） |
| 100倍 | 1.0% |

**加速器が速いほど、中途半端なオフロードは無意味になる。**

### 2.3 分断のコストは実在し、予測の8倍大きい（中核実験）

オフロード率50%固定・計算量同一で、境界数だけを変えた結果。

| 配置パターン | 境界数 | decode | 増分 |
|---|---|---|---|
| `GGGG…GGGG CCCC…CCCC` | 2 | 293.71 ms | +0.00 |
| `GGGGGG CCCCCC …` | 6 | 296.70 ms | +2.99 |
| `GGCC GGCC …` | 18 | 299.49 ms | +5.77 |
| `GCGCGCGC…` | 36 | 306.85 ms | **+13.14** |

| 手法 | 傾き | 95%信頼区間 | 判定 |
|---|---|---|---|
| 単純な最小二乗 | 365.4 µs/境界 | 146.7 〜 584.0 µs | 有意 |
| 対応のある回帰（反復をブロック因子とする） | 365.4 µs/境界 | 180.5 〜 550.2 µs | 有意 |

事前予測は約45 µs（hidden_state 4KBの転送実測）だったが、**実測は365 µsで8.1倍**。転送そのものでは説明がつかず、**デバイス切替に伴う同期とパイプラインの分断**が主因と考えられる。連続配置ならGPUは18層分のカーネルを非同期に投入し続けられるが、交互配置では層ごとにGPUキューの排出を待つため、非同期実行の重ね合わせが失われる。

（同期以外の要因を分離する実験は行っていないため、最有力の説明であって確定ではない。）

### 2.4 prefill と decode は効き方が2倍以上違う

| | 全CPU | 全GPU | 高速化 |
|---|---|---|---|
| TTFT（prefill主体） | 1414.1 ms | 90.2 ms | **15.68倍** |
| decode | 500.68 ms | 72.50 ms | 6.91倍 |

prefillは計算律速でGPUの演算性能がそのまま効くが、decodeはbatch=1でGPUを使い切れない。**「オフロードの効果」は単一の数字では語れない。**

### 2.5 独立実装でも同じ形状（Step 4）

llama.cpp（Vulkan、Q4_K_M、同一モデル）で `-ngl` を振った結果、**正規化した曲線形状の相関 r = 0.9889**。仮説①②は自前ハーネス固有の人工物ではない。

| | 本実装 (PyTorch, fp32) | llama.cpp (Vulkan, Q4_K_M) |
|---|---|---|
| 層数への線形性 | R²=0.9954 | R²=0.9851 |
| 全体の高速化 R | 6.91倍 | 14.44倍 |
| 50%オフロード時 | 全体の伸びの14.0% | 同8.2% |

## 3. 実務への含意

| # | 含意 |
|---|---|
| 1 | **オフロードは「全部載せる」を目指すべき**。載りきらないなら、期待できる効果は 1/(R+1) 程度と見積もる |
| 2 | **オフロード率とは独立に「連続した塊にできるか」が設計変数になる**。非対応オペレータで断片化すると、同じオフロード率でも遅くなる |
| 3 | **prefillとdecodeを分けて評価する**。片方の数字で全体を語らない |
| 4 | **メモリ帯域からの理論値は上限であって予測ではない**。batch=1では固定オーバーヘッドが支配的になりうる（2.6参照） |

### 2.6 補足: batch=1のdecodeは帯域律速ではない

全層GPU配置で精度を変えて測った結果。

| 実装 | decode | 重み | 理論下限 | 理論比 |
|---|---|---|---|---|
| PyTorch fp32 | 67.98 ms | 11.51 GiB | 15.60 ms | 4.36倍 |
| PyTorch bf16 | **81.94 ms** | 5.86 GiB | 7.95 ms | 10.31倍 |
| llama.cpp Q4_K_M | 6.14 ms | 1.96 GiB | 2.66 ms | 2.31倍 |

**bf16は読み出し量が半分なのに、fp32より遅い。** データ量を減らしても速くならない以上、律速しているのは層あたりの固定オーバーヘッド（カーネル起動・Pythonディスパッチ）である。

| 実装 | 層あたりのオーバーヘッド（概算） |
|---|---|
| PyTorch（素の transformers） | 約 1.9 ms/層 |
| llama.cpp | 約 0.17 ms/層 |

ただし本検証はPyTorch側を最適化していない（`torch.compile`・CUDA Graphs・量子化いずれも未適用）。**「PyTorchの限界」ではなく「素の`transformers`推論ループの限界」と理解すべき。**

## 4. 本検証の限界

| # | 限界 |
|---|---|
| 1 | **PC環境（据置GPU + x86 CPU）の値であり、エッジNPUの性能予測には使えない**。電力クラス・帯域の性質・量子化データパスがいずれも異なる |
| 2 | 境界コスト365 µsの内訳（同期／カーネル起動／キャッシュ）は分離していない |
| 3 | 「どの層を載せるか」（前方/後方）は検証していない。全層が同一構造・同一サイズであり、線形性（R²=0.995）がその妥当性を裏づけるため、速度の観点では問題にならないと判断した |
| 4 | 対象は Qwen2.5-3B のみ。モデル構造が大きく異なる場合（MoE等）は別途検証が要る |
| 5 | PyTorch側は最適化なし（2.6参照） |

## 5. 環境（実測値）

| 項目 | 値 |
|---|---|
| CPU | Intel Core i7-10700F（8コア16スレッド、AVX2まで。AVX-512/bf16命令なし） |
| CPUメモリ帯域 | 26.3 GB/s |
| GPU | NVIDIA GeForce RTX 5070 Ti（sm_120、VRAM 15.92 GiB） |
| GPUメモリ帯域 | 791.8 GB/s（CPUの30.1倍） |
| GPU fp32 GEMM | 31.7 TFLOPS |
| デバイス境界の転送（4KB） | 39.5〜49.9 µs（帯域ではなく同期レイテンシ支配） |

**計測には空きRAM 15GB以上・空きVRAM 13GB以上が必要。** 他プロセス（`llama-server` 等）がメモリを占有しているとスワップにより最大140倍の速度劣化が起きる。詳細は実験記録参照。
