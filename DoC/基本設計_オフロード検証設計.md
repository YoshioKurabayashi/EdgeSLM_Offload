## 1. 本書の位置づけ

要件定義書で定めた要件（FR-1〜FR-8）を、実装可能な設計に落とす。特に次の3点を確定させる。

1. 層をデバイスに割り当てる具体的な手段と、埋め込み層・出力層の扱い（要件定義書 未決事項#3）
2. 計測の対象と方法（何をいつ計測し、GPU非同期実行をどう扱うか）
3. 検証すべき定量的な仮説（実験前に予測を立て、実測と突き合わせる）

## 2. 対象モデルの構造（実測値）

`Qwen/Qwen2.5-3B-Instruct` の `config.json` から確定した構造。

| 項目 | 値 |
|---|---|
| アーキテクチャ | `Qwen2ForCausalLM` |
| 層数（`num_hidden_layers`） | **36** |
| 隠れ次元（`hidden_size`） | 2048 |
| FFN中間次元（`intermediate_size`） | 11008 |
| Attentionヘッド数 | 16 |
| KVヘッド数（`num_key_value_heads`） | 2（GQA） |
| 語彙サイズ（`vocab_size`） | 151936 |
| **重み共有（`tie_word_embeddings`）** | **true** |

### 2.1 パラメータとメモリ占有の内訳（fp32）

| 部位 | 内訳 | パラメータ数 | fp32サイズ |
|---|---|---|---|
| decoder層 1層あたり | q/k/v/o_proj + gate/up/down_proj | 76.9 M | **307.7 MB** |
| decoder層 36層合計 | | 2.77 B | 11.08 GB |
| 埋め込み行列（`embed_tokens`） | 151936 × 2048 | 311 M | **1.245 GB** |
| **合計** | | **3.08 B** | **12.33 GB（11.48 GiB）** |

要件定義書3.3節で実測したVRAM占有 11.50 GiB と一致する。

### 2.2 重み共有（tie_word_embeddings）の意味

**`lm_head` は `embed_tokens` と同一のテンソルを共有している。** 別々の重みではなく、1枚の 151936×2048 行列を、入力側では「行の取り出し」、出力側では「転置しての行列積」として使い回している。

これは配置設計に決定的な制約を課す:

> **`embed_tokens` と `lm_head` は同じデバイスに置かなければならない**（同一のテンソルなので分離できない）。

要件定義書 未決事項#3 は「両者を別々にどう置くか」を課題としていたが、実際には**1つの配置決定**に帰着する。

## 4. 層配置の設計

### 4.1 割り当ての手段

`accelerate` の `dispatch_model()` を用いる。モジュール名をキー、デバイスを値とする辞書（`device_map`）を渡すことで、モジュール単位の配置を指定できる。

```python
device_map = {
    "model.embed_tokens": 0,        # GPU（4.2節参照）
    "model.rotary_emb":   0,
    "model.layers.0":     0,        # 以下、層ごとに "cpu" または 0
    "model.layers.1":     "cpu",
    #  ... 中略（36層） ...
    "model.layers.35":    "cpu",
    "model.norm":         0,
    "lm_head":            0,        # embed_tokens と同一デバイス必須
}
```

`dispatch_model()` は各モジュールにフックを取り付け、**入力テンソルが違うデバイスにある場合に自動で転送する**。本検証で測りたい「境界を跨ぐコスト」は、まさにこのフックが行う転送のコストである。自前で転送処理を書く必要はない。

### 4.2 埋め込み層・出力層の配置 → **GPU固定**（未決事項#3の解決）

**結論: `embed_tokens` / `lm_head` は全条件で GPU に固定する。**

理由は `lm_head` の計算コストにある。`lm_head` は 151936×2048 の行列との積であり、1トークンごとに **1.245 GB を読み出す**。デバイス別の所要時間は次のとおり。

| 配置 | 1トークンあたりの `lm_head` 時間 |
|---|---|
| CPU固定 | 1245 MB ÷ 26.3 GB/s = **47.3 ms** |
| GPU固定 | 1245 MB ÷ 791.8 GB/s = **1.57 ms** |

decoder層36層を全てGPUに載せた場合の所要時間は約14.0ms である。ここに `lm_head` をCPU固定で加えると **47.3ms が上乗せされ、全体の77%を占めてしまう**。

これは致命的である。**測定したい decoder層の配置効果が、`lm_head` という固定費に埋もれて曲線が平坦化する。** 要件定義書の当初案（CPU固定）はこの点で不適切だった。

GPU固定であれば上乗せは 1.57ms（全GPU時の約10%）に収まり、かつ**全条件で同一の固定費**となるため、条件間の比較を歪めない。

| 案 | 上乗せ | 判定 |
|---|---|---|
| CPU固定 | 47.3 ms | ✕ 曲線が平坦化する |
| **GPU固定** | **1.57 ms** | **○ 採用** |
| 最終層に追従 | 条件により変動 | ✕ 条件間に不連続が生じる |

**副作用として、オフロード率0%の条件も「純粋な全CPU実行」ではなくなる**（埋め込みと出力層はGPU上にある）。本検証が測るのは **decoder層36層の配置効果**であり、埋め込み・出力層は全条件共通の定数として扱う——この点を結果報告時に明記する。

VRAM占有は 1.245 GB が常時。全層GPU時の合計 11.48 GiB は空き 14.66 GiB に収まることを実測確認済み。

### 4.3 配置パターンの生成（FR-1-2）

`placement.py` が次の3方式で `list[str]`（長さ36、各要素が `"cpu"` または `"cuda"`）を生成する。

| 方式 | パラメータ | 生成規則 |
|---|---|---|
| `contiguous` | `n_gpu` | 先頭 `n_gpu` 層をGPU、残りをCPU |
| `blocked` | `block_size` | `block_size` 層ずつGPU/CPUを交互に配置 |
| `explicit` | `layers` | 明示リストをそのまま使用 |

### 4.4 境界数の定義と数え方

**境界（crossing）= 隣接する処理段の間でデバイスが変わる箇所**と定義する。埋め込み層と出力層がGPU固定であるため、数え上げの対象は次の系列になる。

```
embed_tokens(GPU) → layer0 → layer1 → ... → layer35 → norm(GPU) → lm_head(GPU)
```

要件定義書2.1節の4水準について、実際の境界数は次のとおり。

| 水準 | ブロックサイズ | 層の配置 | 層間の境界 | 入口/出口の境界 | **合計境界数** |
|---|---|---|---|---|---|
| L1 | 18 | `G×18, C×18` | 1 | 1（layer35→lm_head） | **2** |
| L2 | 6 | `G×6, C×6` ×3 | 5 | 1 | **6** |
| L3 | 2 | `G×2, C×2` ×9 | 17 | 1 | **18** |
| L4 | 1 | `G, C` ×18 | 35 | 1 | **36** |

いずれも先頭層がGPUなので `embed_tokens → layer0` の境界は発生しない。4水準とも**GPU 18層 / CPU 18層でオフロード率は完全に同一**である。

境界数は配置から一意に決まるため、`placement.py` が**解析的に算出**する。実測フックによる数え上げは検証用に1回だけ実施し、解析値と一致することを確認する（FR-3-4）。

## 5. 検証すべき仮説（実験前の予測）

3節の帯域比から、1トークンあたりのdecode時間を次のモデルで予測する。

```
t(n) = (36 - n) × t_cpu_layer + n × t_gpu_layer + t_lm_head
```

| 記号 | 値 | 算出根拠 |
|---|---|---|
| `t_cpu_layer` | 11.7 ms | 307.7 MB ÷ 26.3 GB/s |
| `t_gpu_layer` | 0.389 ms | 307.7 MB ÷ 791.8 GB/s |
| `t_lm_head` | 1.57 ms | 1245 MB ÷ 791.8 GB/s |

### 5.1 仮説①: オフロード率-速度曲線は双曲線を描く

| GPU層数 n | オフロード率 | 予測 decode時間/token | 予測 tokens/sec | n=0比 |
|---|---|---|---|---|
| 0 | 0% | 422.8 ms | **2.37** | 1.00倍 |
| 4 | 11% | 377.5 ms | 2.65 | 1.12倍 |
| 8 | 22% | 332.3 ms | 3.01 | 1.27倍 |
| 12 | 33% | 287.0 ms | 3.48 | 1.47倍 |
| 16 | 44% | 241.8 ms | 4.14 | 1.75倍 |
| **18** | **50%** | **219.1 ms** | **4.56** | **1.93倍** |
| 20 | 56% | 196.6 ms | 5.09 | 2.15倍 |
| 24 | 67% | 151.3 ms | 6.61 | 2.79倍 |
| 28 | 78% | 106.1 ms | 9.43 | 3.98倍 |
| 32 | 89% | 60.8 ms | 16.4 | 6.94倍 |
| 36 | 100% | 15.6 ms | **64.1** | **27.1倍** |

### 5.2 仮説②: 部分オフロードは効果が薄い（本検証の主要な予測）

上表で注目すべきは、**50%オフロードでも1.93倍にしかならない**点である。全体で27.1倍の伸びしろがあるうち、半分載せて得られるのは **7%程度**にすぎない。

理由は単純で、**処理時間が加算だから**である。CPU層1つが11.7ms、GPU層1つが0.389ms。半分ずつなら `18×11.7 + 18×0.389 = 217.5ms` となり、**遅い側が支配する**。速い側をいくら増やしても、遅い側が残っている限り総時間は下がりきらない。

> **仮説: 部分オフロードは、ほぼ全ての層を載せない限り実効的な効果が出ない。曲線は終端付近で急峻に立ち上がる。**

これが実測で確認できれば、本検証の主要な成果となる。llama.cpp の `-ngl` を中途半端な値に設定しても期待ほど速くならないという経験則に、定量的な裏づけを与えることになる。

### 5.3 仮説③: 境界コストは検出限界に近い

L1（境界2回）と L4（境界36回）の差は、境界1回あたり約45µs（要件定義書3.3節の実測）として:

```
(36 - 2) × 45µs ≒ 1.53 ms/token
```

50%オフロード時の decode 時間 219.1ms に対し、**わずか0.70%**である。要件定義書2.3節では約1%と見積もっていたが、より精緻な予測では**さらに小さい**。

**FR-7（ノイズフロアの事前確認）の重要性が増した。** 変動係数が0.7%を下回らなければ、4水準の回帰でも傾きを有意に検出できない。Step 2 の関門は形式的な手続きではなく、実質的な可否判断になる。

なお仮説③が棄却される（＝境界コストが予測より大きい）場合、その差分は転送そのものではなく**デバイス切替に伴う同期・実行パイプラインの分断**に由来すると解釈できる。要件定義書3.3節で「pinnedの方がpageableより遅い＝同期レイテンシ支配」と判明しているため、この方向のズレは十分にありうる。

## 6. 計測設計

### 6.1 計測区間

| ステージ | 定義 | 計測方法 |
|---|---|---|
| `load` | モデルのロードと初回配置 | 参考値。比較対象外 |
| `place` | 配置変更（層のデバイス間移動） | 参考値。比較対象外 |
| `prefill` | プロンプト全体の1回目のforward | TTFTの主成分 |
| `decode_step` | 2トークン目以降、1トークンごとのforward | 本検証の主対象 |

### 6.2 GPU非同期実行への対処

CUDAの演算はカーネル投入後に非同期で進むため、`time.perf_counter()` だけでは投入時刻しか測れない。**全ての計測区間の前後で `torch.cuda.synchronize()` を呼ぶ**こと。

ただし同期自体にコスト（要件定義書3.3節の実測で約40〜50µs）があるため、**decode 1ステップ全体を1区間として測る**方針とし、層ごとの細かい計測は行わない。層ごとに同期を入れると、測定行為そのものが仮説③の信号（1.53ms）と同程度の擾乱を生む。

### 6.3 ウォームアップと反復順序

要件定義書 FR-4-3 のとおり、**同一プロセス内で条件を交互に反復**する。

```
[条件A → 条件B → 条件C → 条件D] → [A → B → C → D] → ...  （これを反復回数だけ繰り返す）
```

条件ごとにまとめて反復する（AAAA→BBBB→…）方式は、時間とともに変化する要因（サーマルスロットリング、OSのメモリ状態）が条件と交絡するため**禁止**とする。各反復ブロックの先頭には捨て計測（ウォームアップ）を1回入れる。

### 6.4 記録項目

| 項目 | 単位 | 備考 |
|---|---|---|
| TTFT | ms | 最初のトークンが得られるまで |
| decode時間 | ms/token | 2トークン目以降の平均 |
| tokens/sec | — | decode時間の逆数 |
| 総生成時間 | ms | |
| ピークRSS | MB | `psutil.Process().memory_info().rss` |
| ピークVRAM | MB | `torch.cuda.max_memory_allocated()` |
| 境界数 | 回 | 解析値（4.4節） |
| 境界転送バイト数 | bytes | 境界数 × hidden_state のサイズ |
| 生成トークンID列 | — | 正しさの確認用（FR-6） |
| 実行時の全設定 | — | 再現性のため（NFR-2） |

## 7. 実行フローの設計

### 7.1 配置変更の方式

**モデルの再ロードは行わない。** CPU上にマスターコピーを保持し、条件ごとに必要な層だけをデバイス間で移動する。

| 方式 | 所要時間 | 判定 |
|---|---|---|
| 条件ごとに再ロード | ディスクから毎回数十秒 | ✕ 遅い |
| **層の移動のみ** | 307.7 MB × 移動層数 ÷ PCIe帯域 | **○ 採用** |

36層全てを移動しても約1〜2秒で済む。RAM上のマスターコピーは12.33 GB で、搭載31.9 GB に収まる。

### 7.2 所要時間の見積もり

生成32トークン、5.1節の予測値を用いた場合。

| スイープ | 条件数 | 反復 | 計測時間 | 配置変更 | 合計 |
|---|---|---|---|---|---|
| オフロード率（FR-4-1） | 10 | 3 | 約3.5分 | 約1分 | **約5分** |
| ノイズフロア（FR-7） | 1 | 10 | 約1.2分 | — | **約1.2分** |
| 境界数（FR-4-2） | 4 | 5 | 約2.3分 | 約1分 | **約3.5分** |

初回のモデルロード（safetensors 5.8GB を読み fp32 へ変換）に1〜2分。**全体で20分程度**と見込む。

要件定義時には帯域の実測前だったため「1スイープ30〜60分」と口頭で見積もっていたが、帯域の実測に基づく再計算により**大幅に短くなる**見通しとなった。所要時間はStep 1完了時に実績で更新する。

### 7.3 正しさの確認（FR-6）

全条件で生成トークンID列を記録し、相互に比較する。greedy デコード（`argmax`）かつ fp32 統一のため、原理的には一致するはずである。

ただし **CPU と GPU では浮動小数点演算の集約順序が異なる**ため、丸め誤差の蓄積により長い生成では分岐しうる。分岐した場合はエラーとせず、**何トークン目で分岐したかを記録**する。分岐位置が生成長に対して十分後方であれば、速度計測の妥当性は損なわれない。

## 11. 本設計で新たに確定した事項
