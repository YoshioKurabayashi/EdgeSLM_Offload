## 2026-09-06 Step 1 スモークテスト: 実装は正しいが、環境が計測に耐えない

### 実施内容

`scripts/smoke_test.py` で、実モデル（Qwen2.5-3B-Instruct、fp32）をロードし、全層GPU配置での動作を確認した。

### 正しく動作した項目

| 確認項目 | 結果 | 判定 |
|---|---|---|
| モデルロード | 51.4秒、36層 | ✓ |
| 埋め込み層・出力層のGPU固定 | `embed_tokens=cuda:0` `lm_head=cuda:0` `norm=cuda:0` | ✓ |
| **重み共有（tie_word_embeddings）** | `True`（同一テンソルであることを実機で確認） | ✓ |
| **境界数（解析値 vs 実測値）** | 全層GPU配置で `analytic=0` / `measured=0.00` | ✓ 一致 |
| VRAM占有 | 11.54 GiB（基本設計の予測 11.48 GiB） | ✓ |

**`placement.py` の解析的な境界数算出と、`model_host.py` のフックによる実測が一致した。** FR-3-4 の中核部分は動作している。

### 発覚した問題

全層GPU配置にもかかわらず、速度が予測から桁違いに外れた。

| 指標 | 実測 | 基本設計5.1節の予測 | 乖離 |
|---|---|---|---|
| decode | **2191.95 ms/token** | 15.6 ms/token | **140倍遅い** |
| TTFT | **169,919 ms** | 約16 ms | 桁違い |

実効演算性能に直すと decode で約2.8 GFLOPS。これは同じマシンのCPU（fp32で490 GFLOPS）より遅く、GPUの数字ではない。

### 切り分け

推測で対処せず、原因を順に潰した。

**① GPU自体は健全**（`scripts/diag_slow.py`）

| サイズ | 時間 | スループット |
|---|---|---|
| 2048³ fp32 GEMM | 0.556 ms | **30.89 TFLOPS** |
| 4096³ fp32 GEMM | 4.330 ms | **31.74 TFLOPS** |

GPUもfp32カーネルも正常。「fp32だとGPUが遅い」という説明は成立しない。

**② システムRAMが枯渇していた** ← 真因

診断実行中のメモリ状況:

```
RAM free: 1.0 GB / 31.9 GB
```

プロセス別の内訳:

| PID | プロセス | Private (GB) | WorkingSet (GB) | 備考 |
|---|---|---|---|---|
| 18636 | python（本診断） | **16.97** | **1.53** | 確保した16.97GBのうち1.53GBしか物理メモリ上にない＝**9割がページアウト** |
| 38320 | **llama-server** | **13.31** | 0.01 | 本プロジェクトとは無関係の別プロセス（13:04起動） |
| 28512 | vmmemWSL | 8.81 | 0.54 | WSL |
| 25344 | vmmem | 4.01 | 0.02 | Docker |

llama-server 13.31 GB + WSL 8.81 GB + Docker 4.01 GB = **約26 GB**が他プロセスに確保されており、31.9 GBの物理メモリに対して fp32モデル（12.33 GB）の居場所がない。

**なぜ全層GPU配置でも遅くなるのか**: 重みをGPUへ移した後もPythonプロセス自体がページアウトされたままであり、1 decode あたり数百回発生するPythonレベルの操作（モデルのオブジェクトグラフ、テンソルのメタデータ、transformersのコード）が、そのたびにページフォルトでディスク読み出しを起こす。GPU上の計算そのものは速くても、それを起動する側が止まっている状態。

診断プロセスを停止すると空きRAMは 1.0 GB → **13.1 GB** に回復した。

### 結論と含意

- **実装の不具合ではない。** 配置・境界計測・重み共有の扱いはいずれも設計どおり動作している
- 原因は環境（他プロセスによるRAM占有）であり、コードを変えても解決しない
- **より重要な点**: FR-7 は境界コストの信号（decode比 0.70%）を検出するために低いばらつきを要求する。ページングが起きる環境では変動係数が桁違いに大きくなり、**中核実験は成立しない**。RAMの確保は「モデルが載るか」以前に、**計測の妥当性そのものの前提条件**である

### 対処と結果

**① llama-server の停止（ユーザー実施）**

VRAMの占有元も同じ `llama-server` だった。コマンドラインは `--model Qwen3.5-9B-UD-Q4_K_XL.gguf -ngl 999 --ctx-size 8192 --port 8090` で、9Bモデルを全層GPUに載せていたため **VRAM 約9.4 GiB + RAM 13.3 GB** を保持していた。ユーザーが停止し、VRAM空き 6.7 → **14.7 GiB**、RAM空き → 17.6 GB に回復。

**② ロード時のピークRAMを削減（コード修正）**

停止後も再びRAMが枯渇（空き0.8 GB）した。プロセスを調べると Private 35.47 GB / WorkingSet 17.54 GB で、12.33 GBのモデルに対して明らかに過大だった。

原因は `from_pretrained(dtype=torch.float32)` の指定。**チェックポイントはbf16(5.8GB)なので、fp32(12.3GB)へ変換する過程で両方が同時に存在し、ピークが18GB規模になる**。

`ModelHost.load()` を「bf16でロード → 層単位でfp32へ変換」に変更した。bf16はfp32の上位16bitなので変換に情報の損失はなく、結果は`dtype=float32`で直接ロードした場合とビット単位で同一になる。

| 指標 | 修正前 | 修正後 |
|---|---|---|
| ロード時間 | 51.4秒 | **5.3〜10.5秒** |
| ピークRSS | 17.54 GiB（Private 35.47 GB） | **13.19 GiB** |

配置変更の所要時間も実測できた: 36層移動で2.2秒、18層で0.7〜0.8秒。基本設計7.1節の見積もり（1〜2秒）と整合する。

- **生成トークン列は4条件すべてで一致**（FR-6-1・FR-6-2を満たす）。fp32統一により、CPU/GPUの演算順序差があっても greedy では同じ結果になることを実機で確認

### 発見: 全GPU側だけ予測から4.5倍外れる

全CPU（441.52ms 対 予測422.8ms）はよく一致するのに、全GPU（69.89ms 対 予測15.6ms）だけ大きく外れた。

計測装置（自前フック）が原因かを、同一プロセス・同一モデルでフックの有無だけを変えて切り分けた（`scripts/probe_hook_overhead.py`）。

| | decode |
|---|---|
| フック有り | 66.15 ms/token |
| フック無し | 65.31 ms/token |
| **差（フックのコスト）** | **0.84 ms/token = 1.3%** |

**フックは無実**。フックを外しても予測の4.2倍遅いままであり、原因は計測装置ではない。残る要因は transformers 本体のPythonコスト（1トークンあたり36層×十数個の演算）と、**batch=1 のGEMVがメモリ帯域を使い切れないこと**である。

基本設計3節の予測モデルは「decodeは帯域律速」という仮定で `12.33GB ÷ 791.8GB/s = 15.6ms` としたが、これは帯域を100%使えた場合の理論下限であり、実際にはbatch=1では届かない。**CPU側で予測が当たったのは、CPUの方が帯域利用効率が高い（あるいは他のオーバーヘッドが相対的に小さい）ため**と考えられる。

含意: 実測のダイナミックレンジは 441.52 / 69.89 = **6.3倍**であり、基本設計5.1節が予測した27.1倍より小さい。仮説②（部分オフロードは効果が薄い）の検証には影響しないが、予測表の絶対値は上方修正が必要。

### 予備的な境界コストの兆候

同じオフロード率50%で、境界2回（262.83ms）と境界36回（265.20ms）の差は **2.37ms / 34境界 = 約70 µs/境界**。基本設計5.3節の予測（45µs）と同じオーダーで、相対比は 2.37/263 = **0.90%** と予測（0.70%）よりわずかに大きい。

ただしこれは各条件1回のみの計測であり、統計的な裏づけはない。反復とノイズフロア確認（Step 2以降）を経て判断する。


**乖離1.4%**。基本設計の加算モデル `t(n) = (36-n)×t_cpu + n×t_gpu` が、係数レベルでそのまま成立していることを確認した。tokens/sec はこの逆数なので双曲線になる（プロット②）。

### 仮説②（部分オフロードは効果が薄い）→ **支持された。予測より更に顕著**

| **実測**（n=18相当、内挿） | **約1.83倍** | **約14%** |

さらに直感的な言い方をすると:

> **全体の高速化の半分を得るには、36層のうち32層（89%）をGPUに載せる必要がある。**

処理時間が加算である以上、遅い側が残っている限り総時間は下がらない。「とりあえず半分載せる」という運用は、期待されるほどの効果を生まない。

### 予期していなかった発見: prefill と decode で効き方が2倍以上違う

| | 全CPU | 全GPU | 高速化 |
|---|---|---|---|
| TTFT（prefill主体） | 1414.1 ms | 90.2 ms | **15.68倍** |
| decode | 500.68 ms | 72.50 ms | 6.91倍 |

prefillは計算律速なのでGPUの演算性能がそのまま効くのに対し、decodeはbatch=1でGPUを使い切れず、Pythonオーバーヘッドの比重も上がるため伸びが鈍い。**「オフロードの効果」は単一の数字ではなく、prefillとdecodeで別々に語る必要がある。**

VRAM占有は層数に正確に比例した（n=0で1.20 GiB、n=36で11.54 GiB、1層あたり約0.32 GiB）。

### Step 2 に向けた懸念: 反復間のばらつきが大きい

| 条件 | 平均 | 標準偏差 | 変動係数 |
|---|---|---|---|
| n=0 | 500.68 ms | 18.97 ms | 3.79% |
| n=20 | 252.06 ms | 13.88 ms | 5.50% |
| n=36 | 72.50 ms | 9.73 ms | **13.42%** |

中核実験が必要とする分解能は約0.9%（基本設計5.3節）に対し、**反復間の変動係数は5〜13%と一桁大きい**。反復2が反復1よりほぼ全点で速く、系統的なドリフト（ウォームアップ・サーマル・OS状態）が主因と見られる。

このまま FR-7 のノイズフロア確認（同一条件10回反復の標準偏差）を行うと、**関門を通らない可能性が高い**。

ただし境界数スイープの4条件は各反復ブロック内で連続して測るため、**ドリフトは4条件にほぼ等しく乗る**（交互反復＝FR-4-3 はまさにこれを狙った設計）。したがって、

- 現行の `fit_boundary_cost()` は全データをまとめた単純な最小二乗（反復をブロックとして扱っていない）であり、ドリフトが誤差項に丸ごと入る
- **反復をブロック因子として扱う対応のある分析**（各反復内で条件間の差を取ってから平均する）に変えれば、共通のドリフトが相殺され、必要な分解能に届く可能性がある

Step 2 では FR-7 を設計どおり実施したうえで、上記の対応分析を併せて検討する。

## 2026-09-07 Step 2 ノイズフロア確認（FR-7）: 関門は不合格

`uv run python -X utf8 -m app.cli noise`（同一条件＝50%連続配置を10回反復）。
結果: `results/noise_20260907_084510.csv`

### 実測

| 項目 | 値 |
|---|---|
| n | 10 |
| 平均 | 282.840 ms |
| 標準偏差 | 5.218 ms |
| **変動係数** | **1.845%** |

判定: 予想信号 1.530 ms に対し 2σ = 10.436 ms。**信号がノイズに埋もれる** → FR-7-2 の関門は不合格。

### 副次的な改善: ばらつきは大きく下がった

Step 1 では同種の条件（n=20）で変動係数 5.50% だったのが **1.845% に改善**した。原因は本Stepで導入した `load(initial=...)`——ロード時点で目的の配置に置くようにしたため、計測の合間に層をデバイス間で移動する処理が入らなくなったこと。**配置変更そのものが大きなノイズ源だった。**

（この変更はピークRAM対策として入れたものだが、計測精度の面でも効いた。）

### FR-7 の判定基準そのものの限界

不合格ではあるが、**FR-7 が測っているのは「反復間」の分散**である一方、中核実験で使う対応のある回帰の精度を決めるのは**「反復内」の条件間の分散**である。両者は別物で、FR-7 は保守的な代理指標になっている。

- 境界数スイープの4条件は各反復ブロック内で連続して測るため、反復間のドリフトは4条件にほぼ等しく乗って相殺される
- したがって FR-7 が見ている 5.218 ms のばらつきの大部分は、対応分析では誤差にならない

**厳密な判定基準は、対応のある回帰で得られる傾きの信頼区間そのもの**である。有意にならなければ「境界コストは上限値以下」という定量的な結論が残る（FR-5-3）ので、実施する価値はある。

### 対処

FR-7-2 が定める処方（反復増または生成長延長）のうち、**反復増**を選んだ。対応分析の傾きの標準誤差は `s / sqrt(699 × R)`（R=反復数、699は境界数 2/6/18/36 の反復内平方和）なので、反復を増やすと直接効く。

| 反復数 | 傾きの95%CI半幅（反復内SD=2msと仮定） |
|---|---|
| 5（当初） | 約 73 µs |
| **15（採用）** | **約 38 µs** |

予想される傾きは45〜70 µs/境界なので、反復15なら検出可能圏に入る見込み。ただし反復内SDが実際にどれだけかは未知であり、保守的に見て反復間SD（5.218ms）と同等なら半幅は約100 µsとなり有意にならない。**どちらに転ぶかは実測で決まる。**

### 実装した対応分析

`app/analyze.py` に `fit_boundary_cost_blocked()` を追加した。各反復ごとに平均を引いてから回帰する within 推定で、自由度は n − R − 1。

単体テストで、**ドリフトがあると単純な最小二乗では有意にならないが、対応分析なら検出できる**ことを固定した（`tests/test_analyze.py::TestBlockedRegression`）。傾きの点推定はどちらも真値に一致するが、信頼区間の幅が100分の1以下になる。

## 2026-09-07 Step 3 境界数スイープ（中核実験）: 境界コストを有意に検出

`EDGEOFF_BOUNDARY_SWEEP_REPEATS=15 uv run python -X utf8 -m app.cli boundary`
（4条件 × 15反復 = 60計測、全条件でGPU 18層 / CPU 18層＝オフロード率50%固定）
結果: `results/boundary_20260907_085652.csv` / `.png`

### 実測

| 条件 | 配置パターン（先頭12層） | 境界数 | decode (ms/token) | 境界2回からの増分 |
|---|---|---|---|---|
| `blocked_b18` | `GGGGGGGGGGGG…` | 2 | 293.71 | +0.00 |
| `blocked_b6` | `GGGGGGCCCCCC…` | 6 | 296.70 | +2.99 |
| `blocked_b2` | `GGCCGGCCGGCC…` | 18 | 299.49 | +5.77 |
| `blocked_b1` | `GCGCGCGCGCGC…` | 36 | 306.85 | **+13.14** |

**境界数に対して単調増加**した。4条件は計算量が完全に同一（同じ18層がGPU、18層がCPU）なので、この差はデバイス境界を跨ぐコストのみに由来する。

### 回帰結果

| 手法 | 傾き | 95%信頼区間 | 判定 |
|---|---|---|---|
| 単純な最小二乗 | 365.4 µs/境界 | 146.7 〜 584.0 µs | 有意 |
| **対応のある回帰（本命）** | **365.4 µs/境界** | **180.5 〜 550.2 µs** | **有意** |

**境界コストの検出に成功した。** FR-5-3 の目的を達成し、中核実験は成立した。

### 予測との乖離: 実測は予測の8倍

| | 境界1回あたり |
|---|---|
| 基本設計5.3節の予測（hidden_state 4KB の転送実測から） | 約45 µs |
| **実測** | **365 µs（8.1倍）** |

L1→L4 の差で見ると、予測 1.53 ms（decode比0.70%）に対し **実測 12.42 ms（decode比4.23%）**。**信号は予測より6倍大きく、埋もれる心配は杞憂だった。**

### なぜ8倍になったのか

転送そのもの（4KB）は実測45µsで説明がつく。残る約320µsの主因は**デバイス切替に伴う同期とパイプラインの分断**と考えられる。

- 連続配置なら、GPUは18層分のカーネルを非同期に投入し続けられる（CPUは投入だけして待たない）
- 交互配置では層ごとにGPU→CPUの受け渡しが発生し、そのたびにGPUキューを排出し切るまで待つ。**非同期実行による重ね合わせが完全に失われる**

要件定義書3.3節で「pinnedの方がpageableより遅い＝帯域ではなく同期レイテンシが支配的」と判明していたことと整合する。基本設計2.3節に記した「実際に効くのは転送量ではなく同期回数」という見立てが、定量的に裏づけられた形になる。

ただし**同期以外の要因（カーネル起動オーバーヘッド、CPU側キャッシュの挙動等）を分離する実験は行っていない**ため、「同期が主因」は最有力の説明であって確定ではない。

### FR-7 の関門は「保守的すぎた」

Step 2 で FR-7 は不合格（予想信号1.53ms < 2σ=10.44ms）だったが、実際には有意に検出できた。理由は2つ:

1. **予想信号が6倍過小だった**（実測12.42ms）
2. FR-7 は反復間の分散を見るが、判定に必要なのは回帰の標準誤差である

なお興味深いことに、**反復内の残差SD（9.66 ms）は反復間SD（5.22 ms）より大きかった**。つまり Step 1 で想定した「反復間ドリフトが主要なノイズ源」という見立ては、`load(initial=...)` 導入後は当てはまらなくなっていた。そのため対応分析による改善は限定的（CI幅 437µs → 370µs）で、**有意性を得た主因は反復数を5→15に増やしたこと**である。

対応のある回帰は無駄ではなかった（CIは15%狭くなった）が、**効いたのは統計手法よりサンプル数だった**——これは事前の見立てと違っていた点として記録しておく。

### 結論

> **同じ18層をGPUに載せても、配置が断片的だと遅くなる。** 36層を1層おきに交互配置すると、連続配置に比べて decode が 4.23% 遅い。境界1回あたり 365 µs（95%CI: 181〜550 µs）のコストが乗る。

部分オフロードを設計する際は、オフロード率だけでなく**「連続した塊にできるか」が独立した設計変数になる**。

## 2026-09-07 Step 4 llama.cpp 対照検証（FR-8）: 形状は独立実装でも再現

### 準備で判明したこと

- **llama.cpp のVulkanビルドは既に手元にあった**（`D:/llama-cpp_Vulkan/`、`ggml-vulkan.dll` 込み）。基本設計9節で「ビルド済みバイナリを使う」としていた前提が、そもそも満たされていた。Vulkan SDK の導入もバイナリ取得も不要。
- **未決事項#4（VulkanがRTX 5070 Ti / sm_120 で動くか）→ 解決**。`llama-bench --list-devices` が `NVIDIA GeForce RTX 5070 Ti | fp16: 1 | bf16: 1 | matrix cores: NV_coopmat2` を認識。
- GGUF は Qwen公式リポジトリ `Qwen/Qwen2.5-3B-Instruct-GGUF` から `qwen2.5-3b-instruct-q4_k_m.gguf`（2007.4 MiB）を取得。PyTorch側と同一モデルなので、差は「実装＋量子化」に絞られる。

実行:
```
llama-bench.exe -m qwen2.5-3b-instruct-q4_k_m.gguf -ngl 0,4,...,36 -p 32 -n 32 -t 8 -r 3
```
結果: `results/llamacpp_ngl.csv` / `results/compare_llamacpp.png`

### 比較結果

| | 本実装 (PyTorch, fp32) | llama.cpp (Vulkan, Q4_K_M) |
|---|---|---|
| decode（全CPU → 全GPU） | 500.68 → 72.50 ms | 88.68 → **6.14 ms** |
| 全体の高速化 R | 6.91倍 | **14.44倍** |
| 層数への線形性 | −11.459 ms/層、R²=0.9954 | −2.203 ms/層、R²=0.9851 |
| 50%オフロード時 | 1.83倍（全体の伸びの14.0%） | 2.10倍（同 **8.2%**） |

**正規化した曲線形状の相関係数 r = 0.9889。**

### 結論: 仮説①②は独立実装でも再現した

- **仮説①（decode時間は層数に線形）**: llama.cpp でも R²=0.9851。加算モデルは実装非依存。
- **仮説②（部分オフロードは効果が薄い）**: llama.cpp では**さらに顕著**（50%で全体の8.2%）。

本検証の結論が、自前のPyTorchハーネス固有の人工物ではないことが確認できた。

### llama.cpp の方が全体の高速化が大きい理由

R が 6.91倍 対 14.44倍 と2倍以上違う。これは Step 1 で見つけた「PyTorch側の全GPU端はオーバーヘッド律速」という所見と整合する。

| 実装 | 全GPU時の実測 | 帯域からの理論下限 | 理論比 |
|---|---|---|---|
| PyTorch (fp32, 12.33GB) | 72.50 ms | 15.6 ms | 4.6倍 |
| llama.cpp (Q4_K_M, 2.0GB) | 6.14 ms | 2.54 ms | **2.4倍** |

C++実装でフレームワークのオーバーヘッドが小さいぶん、llama.cpp の方が帯域限界に近い。**GPU端が速くなるほど R が大きくなる。**

### 導かれた一般則: 50%オフロードで得られるのは 1/(R+1)

加算モデル `t(n) = (N−n)·tc + n·tg` から閉じた式が導ける。オフロード率 f のときの高速化は

```
S(f) = 1 / ((1−f) + f/R)          R = tc/tg = 全体の高速化
```

f=0.5 を代入すると `S = 2R/(R+1)` となり、全体の伸びに占める割合は

```
(S − 1) / (R − 1) = 1 / (R + 1)
```

| 実装 | R | 理論 1/(R+1) | 実測 |
|---|---|---|---|
| PyTorch | 6.91 | 12.6% | 14.0% |
| llama.cpp | 14.44 | 6.5% | 8.2% |

実測が理論をやや上回るのは曲線が完全な直線ではないためだが、**「R が大きいほど部分オフロードの効率が下がる」という関係が両実装で確認できた**。

> **加速器が速いほど、中途半端なオフロードは無意味になる。**
> CPU比10倍の加速器なら50%載せても全体の伸びの9%、100倍なら1%しか得られない。

これは Step 1〜3 で得た経験則に、実装非依存の理論的な裏づけを与えるものである。

### 比較上の注意（記録）

FR-8-3 のとおり絶対値は比較していない。加えて、埋め込み層・出力層の扱いが両者で異なる。

| | 埋め込み・出力層 |
|---|---|
| 本実装 | 常にGPU固定（基本設計4.2節） |
| llama.cpp `-ngl n` | n が層数を超えるまでCPU側 |

そのため曲線の切片も一致しない。**一致を主張しているのは正規化した形状のみ。**

## 2026-09-07 補足検証: 「GPUではllama.cppの方が良いのか」への回答

ユーザーからの問い。Step 4 の数字（PyTorch 72.50ms 対 llama.cpp 6.14ms）は一見そう見えるが、
**そのままでは実装の優劣の根拠にならない**。PyTorchはfp32（12.33GB）、llama.cppはQ4_K_M（2.0GB）で
読み出し量が6倍違うためである（FR-8-3 で絶対値比較を禁じた理由そのもの）。

そこで条件を揃え直した。fp32統一は「CPU側でbf16が使い物にならない」制約から選んだものだが、
**全層GPU配置ならCPU側の層は存在しない**ので、この制約は効かない。全層GPU限定でbf16も測った。

### 結果（`scripts/probe_fair_compare.py`）

| 実装 | decode | 重み | 帯域からの理論下限 | 理論比 | 実効帯域 |
|---|---|---|---|---|---|
| PyTorch fp32 | 67.98 ms | 11.51 GiB | 15.60 ms | 4.36倍 | 181.7 GB/s |
| PyTorch bf16 | **81.94 ms** | 5.86 GiB | 7.95 ms | **10.31倍** | 76.8 GB/s |
| llama.cpp Q4_K_M | 6.14 ms | 1.96 GiB | 2.66 ms | **2.31倍** | 342.8 GB/s |

### 決定的な観察: bf16は読み出し量が半分なのに、fp32より遅い

これは **batch=1のdecodeが帯域律速ではない**ことを意味する。データ量を半分にしても速くならない以上、
律速しているのは**層あたりの固定オーバーヘッド**（カーネル起動、Pythonのディスパッチ、
テンソルのメタデータ処理）である。

| 実装 | 層あたりのオーバーヘッド（概算） |
|---|---|
| PyTorch | 約 1.9 ms/層（68ms ÷ 36層） |
| llama.cpp | 約 0.17 ms/層（6.14ms ÷ 36層） |

**約11倍の差**。llama.cppの優位は量子化だけでなく、この固定コストの小ささが本体である。

### 回答

> **batch=1のGPU推論に限れば、llama.cppの方が明確に優れている。** ただし理由はStep 4の数字が
> 示唆するものとは違う。量子化（6倍のデータ削減）ではなく、**層あたりのフレームワーク
> オーバーヘッドが1桁小さいこと**が主因である。PyTorchはGPU速度域に入るとこの固定費が支配的になり、
> データ量を減らしても速くならない。

ただし本検証はPyTorchを最適化していない（`torch.compile`、CUDA Graphs、量子化はいずれも未適用）。
これらを使えばPyTorch側の固定費は大きく下がりうるため、**「PyTorchという枠組みの限界」ではなく
「素の`transformers`の推論ループの限界」と理解すべき**である。

### 計測上の落とし穴（記録）

当初、同一プロセス内でfp32とbf16を続けて測ったところ、bf16が **872.51 ms/token** という
異常値になった。別プロセスで測り直すと **82.88 ms/token** で、10倍以上の差があった。
先に確保したモデルのメモリが解放しきれず、後の計測を汚染していたと考えられる。

**dtypeやモデルを変えて比較する際は、必ず別プロセスで測ること。** `scripts/probe_fair_compare.py`
は子プロセスを起動してこれを回避している。この教訓は Step 1 のRAM枯渇問題と同根である。
