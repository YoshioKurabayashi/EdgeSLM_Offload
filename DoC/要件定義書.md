## 1. 背景・目的

### 1.1 背景

既存プロジェクト EdgeSLM（`D:\AI\source\n_chap5\EdgeSLM`）は、エッジ端末へSLMを搭載するための推論サービスを ONNX Runtime + CPU実行前提で検証してきた。その過程で、decode 1トークンの89.2%が量子化行列積（`MatMulNBits`）であり、速度改善はグルーコードではなく計算カーネルをどのハードウェアに載せるかで決まることが実測で判明している。

一方で「モデル全体を1つのアクセラレータに載せる」以外に、**モデルの一部の層だけをアクセラレータに載せ、残りをCPUで処理する**という実行形態（部分オフロード）が存在する。llama.cpp の `-ngl` オプションが代表例である。この形態がどのような性能特性を持つのかは、EdgeSLM本線では検証されていない。

### 1.2 目的

本プロジェクトは、**部分オフロード（モデルの一部の層をGPUに載せる実行形態）そのものの挙動を、PC環境で定量的に把握する**ことを目的とする。具体的には次の2点を明らかにする。

1. **オフロード率と速度の関係**: GPUに載せる層の割合を0%から100%まで変化させたとき、TTFT・tokens/sec がどのような曲線を描くか。線形か、飽和点があるか。prefill と decode で応答が異なるか。
2. **デバイス境界を跨ぐコスト**: オフロード率が同じでも、層の配置が「連続（境界が少ない）」か「断片的（境界が多い）」かで速度が変わるか。変わるならその単位コストはいくらか。

### 1.3 位置づけ

- 本プロジェクトは **EdgeSLM とは独立した別プロジェクト**である。EdgeSLM のソースコード・ドキュメントには一切変更を加えない。
- EdgeSLM の Phase B（Qualcomm SoC / QNN 実機）への正式なインプットとしては位置づけない。得られる知見は**あくまで参考**である。
- 本検証で得られる数値は PC環境（NVIDIA GPU + x86 CPU）のものであり、エッジ端末の NPU/HTP の性能予測には使用しない。EdgeSLM 側で既に「PC GPU実測はNPU性能の代理指標にならない」と結論づけられており（`EdgeSLM/DoC/基本設計_高速化設計.md` 3.5節⑤）、本プロジェクトはその判断を覆すものではない。

## 2. 検証の考え方

### 2.1 中核となる実験

単に「GPUに載せると速い」ことを確認しても情報量が乏しい。本検証の中核は、**オフロード率を固定したまま境界数だけを変える**比較に置く。

Qwen2.5-3B は36層である。オフロード率50%（18層をGPU）を保ったまま、ブロックサイズを変えることで境界数だけを振ることができる。

| 水準 | ブロックサイズ | 配置パターン | 境界数 | オフロード率 |
|---|---|---|---|---|
| L1 | 18層 | `G×18, C×18` | 1 | 50% |
| L2 | 6層 | `G×6, C×6` を3回 | 5 | 50% |
| L3 | 2層 | `G×2, C×2` を9回 | 17 | 50% |
| L4 | 1層 | `G, C` を18回 | 35 | 50% |

4水準は**オフロード率が完全に同一**なので、計算そのものに要する時間は理論上同じである。したがって水準間の差は境界を跨ぐコストのみに由来し、境界数に対する回帰直線の傾きが**境界1回あたりの単位コスト**を与える。

2点比較ではなく4水準の傾きを見る設計にしたのは、後述（2.3）のとおり信号が小さいと予想されるためである。

### 2.2 副次的な測定

- **オフロード率スイープ**: GPUに載せる層数を 0, 4, 8, ..., 36 の10点で振り、連続配置での曲線を得る。
- **prefill / decode の分離**: 両者は律速要因が異なる（prefill は計算律速、decode はメモリ帯域律速）ため、同じオフロード率でも応答が異なる可能性がある。分離して記録する。

### 2.3 事前に把握しているリスク

**境界コストの信号がノイズに埋もれる可能性がある。**

事前測定（3.3節）により、境界1回あたりのコストは約40〜50µsと判明している。L1（境界1回）と L4（境界35回）の差は 34 × 約45µs ≒ **約1.5ms/token** と見積もられる。一方 decode は50%オフロード時に150ms/token前後と予想され、比率にして**約1%**にとどまる。

このため、計測ノイズが十分小さいことを先に確認する手順を必須とする（FR-7）。ノイズが信号を上回る場合は、反復回数の増加または生成トークン数の延長で対処する。**「傾きがゼロだった（境界コストは無視できる）」も本検証の妥当な結論**であり、その場合も定量的な上限値（信頼区間）を示す。

### 3.2 ソフトウェア

| 項目 | 値 | 備考 |
|---|---|---|
| torch | 2.11.0+cu128 | EdgeSLM の `.venv` で確認。sm_120 で**実演算まで成功**を確認済み |
| Python | 3.12 | |
| パッケージ管理 | uv | n_chap5シリーズの作法を踏襲 |
| CUDA Toolkit (nvcc) | 12.1 | **sm_120 のソースビルドには不足**。本プロジェクトでは nvcc を使用しない |
| Vulkan SDK | 未導入（`glslc` なし） | llama.cpp はビルド済みバイナリを使うため導入不要 |

### 3.3 事前実測値

**CPU行列積スループット（1024³、8スレッド）**

| dtype | 時間 | スループット | fp32比 |
|---|---|---|---|
| float32 | 4.3 ms | **495.74 GFLOPS** | 1.00 |
| bfloat16 | 2700.5 ms | 0.80 GFLOPS | **1/620** |
| float16 | 2916.8 ms | 0.74 GFLOPS | 1/670 |

参考: 同一サイズの GPU bf16 は 0.034 ms / 62608.85 GFLOPS。

**メモリ読み出し帯域（512 MiB の総和演算、2026-09-06追加実測）**

| デバイス | 帯域 |
|---|---|
| CPU | **26.3 GB/s** |
| GPU | **791.8 GB/s** |

比は **30.1倍**。batch=1 の decode はメモリ帯域律速となるため、基本設計5節の性能予測はこの値を用いる。

**デバイス境界の転送コスト（hidden_state `(1,1,2048)` bf16 = 4KB）**

| 経路 | 時間 |
|---|---|
| pageable CPU→GPU | 39.5 µs |
| pinned CPU→GPU | 49.9 µs |
| GPU→CPU | 48.8 µs |

pinned が pageable より遅いことから、**このサイズの転送コストは帯域ではなく同期のレイテンシが支配的**と判断できる。すなわち境界コストはテンソルサイズにほぼ依存せず、境界1回あたり約40〜50µsの固定費として扱える。

**VRAM占有**

| 精度 | 重みのサイズ | 全層GPU配置の可否 |
|---|---|---|
| fp32 | 11.50 GiB | **可**（確保後の残り 3.16 GiB、実測確認済み） |
| bf16 | 5.75 GiB | 可 |

### 3.4 bf16が遅い原因の切り分け（実測）

3.3節のbf16の遅さが「ハードウェアがbf16を扱えない」ことによるものか、「ソフトウェアのカーネル選択」によるものかを切り分けた（1024³、8スレッド）。

| # | 条件 | 時間 | スループット |
|---|---|---|---|
| (1) | fp32のまま行列積 | 4.39 ms | 489.61 GFLOPS |
| (2) | bf16 → fp32 への変換のみ | 0.39 ms | — |
| (3) | **bf16を fp32に変換してから行列積** | **5.23 ms** | **410.37 GFLOPS** |
| (4) | bf16のまま行列積（PyTorch既定） | 2703.65 ms | 0.79 GFLOPS |

`torch.backends.cpu.get_cpu_capability()` は **AVX2** を返す（AVX-512非搭載を裏づけ）。

**(3)が410 GFLOPS出ている**ことが決定的である。bf16のデータ自体はこのCPUで問題なく扱え、fp32への変換コストもわずか0.39ms（bf16はfp32の上位16bitであり、変換は実質ビット操作のため）。それにもかかわらず(4)は(3)の**517倍**遅い。

したがって原因は次のとおり:

- 本機はAVX-512を持たず、ネイティブなbf16積和命令（**AVX512-BF16 / `VDPBF16PS`**）が存在しない
- ネイティブbf16命令のないハードウェアでは、PyTorch/oneDNNはbf16向けの最適化GEMMカーネルを持たず、ベクトル化もキャッシュブロッキングも効かない汎用フォールバックパスに落ちる
- 「内部でfp32に変換してから最適化カーネルを使う」という最適化は自動では行われない — (3)と(4)の517倍差がその証拠

**CPUの絶対性能が不足しているのではない**（fp32では490 GFLOPSと十分な速度が出ている）。**bf16というデータ型を選んだ瞬間に最適化パスから外れる**、というソフトウェア側の問題である。

## 4. スコープ

### 4.1 対象

- 対象モデル: **Qwen2.5-3B-Instruct**（36層、hidden_size 2048、3.086Bパラメータ）。EdgeSLM本線と同一モデルとし、既存の実測値と傾向を突き合わせられるようにする。
- 主軸フレームワーク: **PyTorch + accelerate**（層単位のデバイス配置を任意に制御できる唯一の選択肢のため）
- 対照フレームワーク: **llama.cpp（Vulkanバックエンド、ビルド済みバイナリ）**

### 4.2 対象外

以下は EdgeSLM 本線またはその Phase B の領域であり、本プロジェクトでは扱わない。

- ONNX Runtime の DirectML EP / QNN EP
- ONNXモデルの再変換、量子化形式（QDQ / MatMulNBits）の検討
- Qualcomm SoC 実機・QNN SDK
- C++移植、Android統合
- 推論の正しさ（生成品質）の評価。ただし全層GPU時の出力が参照実装と一致することの確認は行う（FR-6）

## 5. 機能要件

### FR-1: 層配置ポリシー

| ID | 要件 |
|---|---|
| FR-1-1 | 36層それぞれを CPU/GPU のどちらに配置するかを、設定で指定できること |
| FR-1-2 | 配置パターンとして「連続分割（GPU側n層を先頭から）」「ブロック交互分割（ブロックサイズ指定）」「明示リスト」の3方式をサポートすること |
| FR-1-3 | 埋め込み層（`embed_tokens`）と出力層（`lm_head`）の配置を明示的に指定できること。**既定はGPU固定**とし、全水準で固定する（比較条件を揃えるため）<br>※初版では既定をCPUとしていたが、基本設計4.2節の検討により変更した。`lm_head` をCPUに置くと1トークンあたり47.3msの固定費が乗り、全GPU時の77%を占めて曲線が平坦化するため。また `tie_word_embeddings=true` により両者は同一テンソルであり、別々のデバイスには置けない |
| FR-1-4 | KVキャッシュは各層に付随し、その層と同一デバイス上に配置すること。境界を跨ぐのは hidden_state のみとする |

### FR-2: 精度（dtype）

| ID | 要件 |
|---|---|
| FR-2-1 | CPU側・GPU側とも **float32 に統一**すること |
| FR-2-2 | 精度を切り替える設定は持つが、既定値は fp32 とする |

**fp32統一とする理由**: 当初は bf16統一を想定していたが、3.3節の実測により本機の CPU bf16行列積が **fp32の1/620（0.80 GFLOPS）** であることが判明した。bf16統一にすると全CPU配置時の decode が1トークンあたり数秒規模となり、境界コスト（約1.5ms）が完全に埋没して中核実験が成立しない。fp32であれば CPU側もメモリ帯域律速の妥当な速度域に入る。fp32 では GPU側がテンソルコアの恩恵を受けられないが、本検証の目的は絶対性能の測定ではなく**配置のみを変数とした比較**であるため、両デバイスで精度を揃えることを優先する。VRAM は11.50 GiB で全層GPU配置も成立することを実測確認済み（3.3節）。

**補足: この遅さは「CPUがbf16を計算できない」ことによるものではない**（3.4節の切り分け実測を参照）。bf16のデータをfp32に変換してから計算すれば410 GFLOPSが出る。遅いのは、ネイティブなbf16積和命令（AVX512-BF16）を持たないハードウェア上で、PyTorchがbf16のまま計算しようとして最適化GEMMカーネルの対象外となり、事実上スカラー実行のパスに落ちるためである。**したがってこれは本開発機に固有の事情であり、一般論として「bf16は遅い」と解釈してはならない。** ARMはARMv8.6-AでBF16拡張を持ち、近年のSnapdragon SoCはbf16に対応しているため、エッジ実機側では事情が異なる。

### FR-3: 計測

| ID | 要件 |
|---|---|
| FR-3-1 | TTFT（最初のトークンまでの時間）、tokens/sec、総生成時間を計測すること |
| FR-3-2 | prefill と decode を分離して計測すること |
| FR-3-3 | ピークメモリを RAM（RSS）と VRAM の両方で記録すること |
| FR-3-4 | 境界を跨いだ回数と、跨いだテンソルの総バイト数を記録すること |
| FR-3-5 | CPUスレッド数を8（物理コア数）に固定すること |

### FR-4: スイープ実行

| ID | 要件 |
|---|---|
| FR-4-1 | オフロード率スイープ（GPU層数 0,4,8,...,36 の10点、連続配置）を自動実行できること |
| FR-4-2 | 境界数スイープ（2.1節の L1〜L4、オフロード率50%固定）を自動実行できること |
| FR-4-3 | 各条件の計測は、**同一プロセス内で条件を交互に反復**して行うこと。条件ごとに別プロセスを起動する方式は禁止する |
| FR-4-4 | 反復回数はオフロード率スイープで3回、境界数スイープで5回以上とすること |
| FR-4-5 | 生成トークン数は32を既定とすること |

**FR-4-3の理由**: EdgeSLM本線で、別セッションでの単発実行同士を比較した結果、実装差ではなくウォームアップ由来のノイズを「速度差」と誤読しかけた事例がある（`EdgeSLM/DoC/基本設計_高速化設計.md` 3.5節②）。同一セッション内での交互反復を必須とする。

### FR-5: 出力

| ID | 要件 |
|---|---|
| FR-5-1 | 全計測結果を CSV または JSON で `results/` 配下に出力すること |
| FR-5-2 | オフロード率-速度曲線、境界数-速度の回帰直線をプロットできること |
| FR-5-3 | 境界数スイープの結果から、境界1回あたりの単位コストとその信頼区間を算出すること |

### FR-6: 正しさの確認

| ID | 要件 |
|---|---|
| FR-6-1 | 全層GPU配置（n=36）時の生成トークン列が、全層CPU配置（n=0）時と一致することを確認すること |
| FR-6-2 | 境界数スイープの L1〜L4 で、生成トークン列が相互に一致することを確認すること（配置は速度にのみ影響し、出力を変えてはならない） |

fp32統一としたことで、デバイス間の数値差は fp32演算順序に起因する微小なものに限られ、greedy デコードであればトークン列は一致する見込みである。一致しない場合は、その分岐位置を記録する。

### FR-7: ノイズフロアの事前確認

| ID | 要件 |
|---|---|
| FR-7-1 | 境界数スイープの本計測に先立ち、**同一条件を10回反復**して tokens/sec の標準偏差を測定すること |
| FR-7-2 | 予想信号（約1.5ms/token）が標準偏差の2倍を上回らない場合、本計測に進まず、反復回数の増加または生成トークン数の延長で条件を見直すこと |

### FR-8: 対照検証（llama.cpp）

| ID | 要件 |
|---|---|
| FR-8-1 | llama.cpp の公式ビルド済み Windows Vulkan バイナリを用い、`-ngl` を振ったオフロード率スイープを実施すること |
| FR-8-2 | 量子化は GGUF Q4_K_M とする |
| FR-8-3 | PyTorch側（fp32）と llama.cpp側（Q4_K_M）は精度が異なるため、**絶対値は比較せず、正規化した曲線の形状のみを突き合わせる**こと |
| FR-8-4 | llama.cpp は連続分割のみのため、境界数スイープ（FR-4-2）の対象外とする |

| Step | 内容 | 完了条件 | 判断ゲート |
|---|---|---|---|
| 0 | 要件定義・基本設計 | 本書および基本設計書の承認 | — |
